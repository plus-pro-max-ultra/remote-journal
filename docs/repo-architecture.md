Last verified: 2026-11-05, against the live remote. This document explains how the one repository is organized, how the two editions are published, and how editing works in practice. Updated 2026-11-05 for the preview-edition rule in section 2.

## 1. One repository, everything inside

`plus-pro-max-ultra/remote-journal` (public) holds the articles, the build tooling, the site output, and the review material.

Rules now in force:

- Pushing to a review branch or to `preview` needs no approval (MM, 2026-11-04 23:46 and 2026-11-05 00:17). The GitHub Pages site is the working preview; any preview update ships there directly.
- Moving anything onto `main` and the official edition requires MM's explicit approval.
- When a release is approved, the full `preview` state is what ships - the approved articles plus every other edit MM made on the branch, carried over with a complete diff so nothing is missed. The branch wins over any older local or generated copy.
- Cloudflare production stays untouched until that approval.

## 3. What lives where on `main`

- `content/articles/` - the 16 published articles, one JSON file each (text, sources, photos, date).
- `content/topic-queue.json` - the coming-week topic preview queue.
- `ops/publication-ledger.json` - the issue ledger: which article is which issue number and date.
- `ops/RELEASE_CHECKLIST.md` - the steps for a formal release.
- `ops/github-actions/` - reference copies of automation definitions only; no GitHub Actions run. Builds and content checks run locally before anything is pushed; separately, Cloudflare runs its own build and deploy remotely whenever `main` changes.
- `scripts/build_site.py` - the build: validates every article JSON (including a required `YYYY-MM-DD` date), runs the content tests in `tests/`, regenerates the whole site into `dist/`, and syncs it to the repository root.
- `assets/site.css`, `assets/site.js` - shared styles and browser behavior.
- Repository root - the generated site itself: `index.html`, `about/`, `privacy/`, `archive/`, `articles/<slug>/`, `feed.xml`, `sitemap.xml`, `robots.txt`, `404.html`, `sw.js`, icons. These files are generated by the build and are overwritten the next time it runs.

The `preview` branch adds, on top of all of that:

- `drafts/` - the newest unissued draft (currently issue 017, dated 2026-11-04, still unissued).
- `review/ready-drafts/` - the fifteen revised manuscripts. They carry no dates and no issue numbers; none are invented for them.
- A preview layer in `scripts/build_site.py`: renders each draft as a page marked 審閱稿 with noindex and no production canonical, plus a review index at `/preview/`. Drafts stay out of `feed.xml`, `sitemap.xml` and `ops/publication-ledger.json`; the production validator and published pages are unchanged.
- One source-link fix in the preview build: a source whose URL is not HTTPS keeps its exact bibliography entry and true address, marked unverified, instead of being silently dropped (dropping shifted the in-text [n] citation numbering). The production validator's HTTPS rule is unchanged.

## 4. The two editions

- Official edition: https://journal-for-far.learnman.workers.dev/ - a Cloudflare Workers project connected to this repository. Every push to `main` triggers an automatic build and deploy (deploy command `npx wrangler deploy`). Canonical links, RSS, sitemap and social previews all use this address.
- Preview edition: https://plus-pro-max-ultra.github.io/remote-journal/ - serves the `gh-pages` branch, built from `preview`. As of 2026-11-05 the preview build is pushed and queued for its first GitHub Pages deployment (a GitHub Actions/Pages incident was delaying deploys at writing time); until it lands, the address still serves the old mirror. Once live it is the working review site, not a mirror: the 16 published articles plus the 16 review drafts, updating directly whenever `preview` changes, without approval. Published pages still point readers and search engines at the official edition; draft pages are marked as review copies and carry noindex.

## 5. How editing works, and what is safe to edit

Edit on the `preview` branch (or a review branch), not on `main`: any change to `main` triggers an automatic production build and deploy to the official edition, so editing `main` directly publishes rather than saving a draft. On `preview`, MM edits freely through GitHub's web interface or any git tool, with no approval needed - the drafts live at `drafts/` and `review/ready-drafts/` as plain JSON source files. There is no inline web editor; editing means editing the source files. After each `preview` change, the agent rebuilds and redeploys `gh-pages`, so the preview site follows the branch. If the generated files on `gh-pages` itself are ever edited directly, the agent first diffs them against the last deployed build, carries the edits back into the sources, and only then redeploys; anything that cannot be mapped back cleanly is reported instead of overwritten.

Safe to edit directly (these are sources; a rebuild will not erase them):

- `content/articles/*.json` - article text, sources, photo choices.
- `content/topic-queue.json` - topic preview.
- `scripts/build_site.py` - the About and Privacy page text lives here as templates (`ABOUT_BODY`, `PRIVACY_BODY`), plus shared page structure.
- `ops/`, `docs/`, markdown files.

Regenerated on build (edit with care): the HTML at the repository root (`index.html`, `about/index.html`, `privacy/index.html`, `articles/*/index.html`, `feed.xml`, `sitemap.xml`). Direct edits here work, but the next build would overwrite them. The established practice, used for MM's 2026-11-04 About/Privacy edits: MM edits the generated file, the agent ports the same wording into the build source before rebuilding, then diffs the rebuilt output against MM's version to prove nothing was lost.

## 6. Feasibility, verified in practice on 2026-11-04

- MM edited `about/index.html` and `privacy/index.html` through the GitHub web UI on a branch; the changes merged cleanly with the agent's local work and shipped the same day.
- Three full release cycles ran end to end on 2026-11-04: branch push, merge to main, GitHub Pages deploy, and automatic Cloudflare Workers build. All three Workers builds succeeded.
- The content validator gates every build: 16 of 16 articles validated, all content tests pass.
- The daily and batch review branches were pushed and read back through the GitHub API to confirm the remote content matches.

What review looks like today: the GitHub Pages site is becoming the rendered working preview - the build is pushed and its first deployment is pending, after which MM reads and edits the sixteen drafts there, and the site follows the `preview` branch. Other branches still have no rendered preview of their own; reviewing them means source files on GitHub or agent-rendered PDFs and screenshots. The Cloudflare branch-preview build failed on 2026-11-04 and has never produced a usable preview URL.

Remaining limitation: rendered preview exists only for the `preview` branch's content. A one-off branch outside that flow is still reviewed as source or screenshots. GitHub Pages deployments can also lag during GitHub incidents, so a pushed update may take time to appear. The publication ledger at `ops/publication-ledger.json` records which article is which issue number and date.

Promotion after approval: when MM approves content, the agent diffs the full `preview` branch against `main` and carries everything over - each approved article gets its issue number, date and ledger entry and moves into `content/articles/`, and any other edits MM made anywhere on the branch come along. `preview` is then brought back in sync with the new `main`. The fifteen manuscripts predate the multi-page architecture, so their approved content is integrated into the current architecture, never a wholesale merge of the old branch, which would roll back the site structure. Within the approved scope, the branch's wording - including MM's edits - takes precedence.

# 倉庫架構（繁體中文）

以下為 2026-11-05 對線上倉庫實際查核後的說明；當日依第 2 節的預覽站規則更新。

## 1. 單一倉庫

所有文章、建置工具、網站輸出與審閱資料都在 `plus-pro-max-ultra/remote-journal`（公開）這一個倉庫裡。

## 2. 分支角色

以下為 2026-11-05 全部八個分支的快照：

| 分支 | 角色 | 狀態 |
| --- | --- | --- |
| `main` | 目前正式版來源：文章資料、建置腳本、樣式、測試與產生的網站 | 已刊至第 016 期 |
| `preview` | 工作預覽來源：`main` 的全部內容，加上十六篇審閱稿（`drafts/` 與 `review/ready-drafts/`）與預覽建置層 | 供 GitHub Pages 預覽站；你直接在此編輯 |
| `gh-pages` | 僅供發布的分支，服務 GitHub Pages 預覽站 | 由 `preview` 建置產生 |
| `content-readiness-2026-11-04` | 十五篇重修稿的原始審閱分支 | 內容已帶入 `preview`，保留紀錄 |
| `daily-review-2026-11-04` | 第 017 期草稿的原始審閱分支 | 內容已帶入 `preview`，保留紀錄 |
| `architecture-v1` | 已完成的多頁架構工作 | 已併入 main，保留紀錄 |
| `photo-preview` | 早期照片預覽工作 | 停用中；你要清理時可刪 |
| `docs/repo-architecture` | 本說明文件 | 僅文件 |

現行規則：

- 推送到審閱分支或 `preview` 都不需批准（你 2026-11-04 23:46 與 2026-11-05 00:17 的指示）。GitHub Pages 站就是工作預覽站，任何預覽更新都直接發布到那裡。
- 推上 `main` 與正式版需要你明確批准。
- 批准上線時，以 `preview` 的完整內容為準：批准的文章，連同你在分支上做的其他所有修改，都會逐項核對差異後帶入 `main`，確保沒有遺漏；分支內容優先於任何舊的本機或產生副本。
- 批准之前，Cloudflare 正式版保持不變。

## 3. `main` 裡的內容位置

- `content/articles/`：16 篇已刊文章，每篇一個 JSON（內文、來源、照片、日期）。
- `content/topic-queue.json`：未來一週預告的選題佇列。
- `ops/publication-ledger.json`：出刊紀錄，登載哪一篇是第幾期、哪一天。
- `ops/RELEASE_CHECKLIST.md`：正式發布步驟。
- `ops/github-actions/`：自動化定義的參考副本，沒有實際跑 GitHub Actions。建置與內容檢查在本機完成後才推送；另外，`main` 一有變動，Cloudflare 會在遠端自動建置並部署。
- `scripts/build_site.py`：建置程式。驗證每篇 JSON（日期 `YYYY-MM-DD` 為必填）、跑 `tests/` 的內容測試、把整個網站重新產生到 `dist/` 並同步到倉庫根目錄。
- `assets/site.css`、`assets/site.js`：全站共用樣式與瀏覽器行為。
- 倉庫根目錄：產生的網站本體（`index.html`、`about/`、`privacy/`、`archive/`、`articles/`、`feed.xml`、`sitemap.xml`、`robots.txt`、`404.html`、`sw.js` 與圖示）。這些檔案由建置產生，下次建置時會被覆寫。

`preview` 分支在上述之外多了：

- `drafts/`：最新待刊草稿（目前為第 017 期，日期 2026-11-04，尚未刊出）。
- `review/ready-drafts/`：十五篇重修稿。它們沒有日期與期數，預覽站也不會替它們虛構。
- `scripts/build_site.py` 的預覽層：把每篇審閱稿渲染成標示「審閱稿」的頁面（noindex、不帶正式版標準網址），並在 `/preview/` 提供審閱專區索引。審閱稿不進 `feed.xml`、`sitemap.xml` 與出刊紀錄；正式版驗證器與已刊頁面不受影響。
- 預覽建置的一處來源連結修正：非 HTTPS 的來源保留完整書目與原始網址並標示未驗證，不再靜默丟棄（丟棄會讓文內 [數字] 標記與來源編號錯位）；正式版驗證器的 HTTPS 規則不變。

## 4. 兩個版本

- 正式版：https://journal-for-far.learnman.workers.dev/ ，Cloudflare Workers 專案連接此倉庫。每次推送 `main` 會自動建置並部署（部署指令 `npx wrangler deploy`）。標準網址、RSS、網站地圖與分享預覽都用這個網址。
- 預覽版：https://plus-pro-max-ultra.github.io/remote-journal/ ，服務 `gh-pages` 分支，由 `preview` 建置。截至 2026-11-05，預覽建置已推送、等待第一次 GitHub Pages 部署（撰稿時 GitHub Actions/Pages 事故造成部署延遲）；部署完成前，這個網址仍是舊鏡像。上線後它就是工作審閱站而非鏡像：顯示 16 篇已刊文章加 16 篇審閱稿，`preview` 一有變動就直接更新，不需批准。已刊頁面仍把讀者與搜尋引擎導向正式版；審閱稿頁面標示為審閱稿並帶 noindex。

## 5. 你的編輯方式與安全範圍

請在 `preview` 分支（或審閱分支）上編輯，不要直接改 `main`：`main` 一有變動就會觸發正式版的自動建置與部署，所以直接改 `main` 等於發布，而不是儲存草稿。在 `preview` 上，你可以用 GitHub 網頁或任何 git 工具自由編輯，不需批准；草稿就是 `drafts/` 與 `review/ready-drafts/` 裡的 JSON 原始檔。頁面本身沒有線上編輯器，編輯等於修改原始檔。每次 `preview` 變動後，我會重新建置並部署 `gh-pages`，讓預覽站跟上分支。若 `gh-pages` 上產生的檔案被直接修改，重新部署前我會先比對與上次部署的差異，把修改回填到來源，再重新部署；無法對應回來源的修改會回報，不會直接覆蓋。

可以直接改（屬於來源，重建不會洗掉）：

- `content/articles/*.json`：文章內文、來源、照片。
- `content/topic-queue.json`：預告選題。
- `scripts/build_site.py`：關於頁與隱私頁的文字以模板形式在這裡（`ABOUT_BODY`、`PRIVACY_BODY`），以及共用頁面結構。
- `ops/`、`docs/` 與各 markdown 文件。

重建時會覆蓋（直接改有效，但下次建置會被覆寫）：根目錄的 HTML（`index.html`、`about/index.html`、`privacy/index.html`、`articles/*/index.html`、`feed.xml`、`sitemap.xml`）。既定做法（已用於你 2026-11-04 對關於頁／隱私頁的修改）：你改產生的檔案，我在重建前把同樣的文字回填到建置來源，重建後再與你的版本逐行比對，確認沒有遺失。
